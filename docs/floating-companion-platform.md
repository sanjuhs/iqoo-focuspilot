# Floating Mira: Android platform contract

Research checked 2 October 2026 against official Android documentation. Current project: min SDK 28, target SDK 35, compile SDK 36; connected development phone runs API 36. This is an implementation recommendation for the pre-event prototype, not evidence of a shipped or tested overlay. No Android source, APK, device permission or settings were changed for this report.

Build an optional, standalone floating-companion service. Reuse the original native Canvas Mira in a small movable bubble, with explicit Open assistant and Stop controls. Keep the lilac/charcoal/teal design, reduced motion, mute and hide preferences. The service should display local companion/status UI only: no microphone, screen capture, accessibility action, network request, boot receiver, wake lock, screen-on flag or automatic model inference. Existing opt-in usage monitoring and focus timers retain their separate lifecycle and permissions. Stopping the companion must not reset focus, alter a timer or charge the simulated ledger.

## Permission and startup

1. Default floating mode off. Explain the feature in the visible app, then let the user open Android's overlay permission screen. Declare `SYSTEM_ALERT_WINDOW`; use `Settings.ACTION_MANAGE_OVERLAY_PERMISSION` only from the user's permission button. Resolve/catch a missing settings activity. Package-specific URI routing is documented only before Android R, so API 36 can show a general list instead. Treat `Settings.canDrawOverlays(context)` as the current grant check, including on return to the app; there is no grant result to infer from an activity result code. A grant alone is not the application's Enable action. [Settings permission APIs](https://developer.android.com/reference/android/provider/Settings#ACTION_MANAGE_OVERLAY_PERMISSION), [grant check](https://developer.android.com/reference/android/provider/Settings#canDrawOverlays(android.content.Context)).
2. Start from an explicitly tapped Enable button while the activity is visibly resumed. Target 35 narrows the overlay exemption for **background foreground-service starts**: holding the permission is insufficient; an already-visible overlay is also required for that exemption. Avoid solving this with boot/retry/background restarts. Catch `ForegroundServiceStartNotAllowedException` and keep the feature off when launch is refused. [Background service restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [Android 15 changes](https://developer.android.com/about/versions/15/behavior-changes-15#fgs).
3. A persistent, user-selected floating companion is our proposed `specialUse` foreground-service use case. Declare `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_SPECIAL_USE`, service type `specialUse`, and `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE` explaining the local floating UI. On API 34+, pass `FOREGROUND_SERVICE_TYPE_SPECIAL_USE` when promoting the service; version-guard the older-device path. Promote promptly with its notification, and use `exported=false`. This type has no separate runtime prerequisite, but does not grant overlay access. Google Play reviews the declared use case; a manifest declaration establishes no approval. [Service types](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use), [foreground-service launch](https://developer.android.com/develop/background-work/services/fgs/launch).

The notification must identify floating Mira and expose Stop plus Open assistant. Use a dedicated channel/notification ID, separate from the focus monitor. Android does not require `POST_NOTIFICATIONS` to start an FGS, but still requires its notification; denial can remove it from the notification drawer while leaving an Active apps entry. **Our product recommendation** is to require usable notification/channel visibility before enabling this prototype, so notification Stop remains accessible when an overlay is suppressed. Do not automatically grant or repeatedly request notification permission. Keep in-app and bubble Stop controls as well. [Notification permission behavior](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

## Window and touch contract

Use `TYPE_APPLICATION_OVERLAY`, supported throughout this app's min-SDK range. It appears over ordinary activities but under important system UI; Android may change its position, size or visibility. Use one bounded window, approximately 72–112 dp initially, with `FLAG_NOT_FOCUSABLE`, which also permits touches outside the window to go elsewhere. Keep normal touchability within the bubble. Clamp dragging to the usable display area, respecting rotation, cutouts, bars and the keyboard. Avoid full-screen transparent parents, focus capture and attempts to cover system permission controls. [Overlay type and flags](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY).

Application overlays are **untrusted**. Android 12 blocks unsafe touch-through occlusion. The documented opacity exception concerns windows through which touches pass; it does not require an ordinary touchable bubble to have alpha below 0.8. A transparent background inside a large window is not an excuse to make that window full-screen. If a future design adds a non-touchable overlay, check the system's maximum obscuring opacity and combined overlapping-window opacity rather than assuming visual transparency or a hard-coded threshold is sufficient. Never disable Android's untrusted-touch protection for the demo. [Untrusted-touch rules](https://developer.android.com/about/versions/12/behavior-changes-all#untrusted-touch-events), [maximum-opacity API](https://developer.android.com/reference/android/hardware/input/InputManager#getMaximumObscuringOpacityForTouch()).

Other apps can declare `HIDE_OVERLAY_WINDOWS` and call `Window.setHideOverlayWindows(true)` on sensitive screens. Accept the resulting suppression; do not recreate Mira repeatedly, switch overlay types or request accessibility privileges to evade it. Our own command-confirmation/sensitive setup screens may use the same protection if explicitly implemented with the required permission. [Android overlay hiding](https://developer.android.com/about/versions/12/features#hide-application-overlay-windows), [Window API](https://developer.android.com/reference/android/view/Window#setHideOverlayWindows(boolean)).

## Screen, permission and shutdown lifecycle

Use this conservative display eligibility check immediately before attachment and user interactions: floating mode enabled, current overlay grant, device interactive, keyguard not showing. `isInteractive()` is broader than literal screen illumination; `isKeyguardLocked()` reports keyguard showing, including a trivially dismissible lock. Do not use `isDeviceSecure()` as a current-lock test. Register screen-on/off broadcasts at runtime; screen broadcasts cannot be received by manifest receivers. On screen off, remove/hide the window and stop all animation. On screen on or user present, recheck eligibility before restoring an existing, still-enabled service window. Never dismiss keyguard, turn the screen on or wake the CPU for Mira. [Power state](https://developer.android.com/reference/android/os/PowerManager#isInteractive()), [keyguard state](https://developer.android.com/reference/android/app/KeyguardManager#isKeyguardLocked()), [screen broadcast contract](https://developer.android.com/reference/android/content/Intent#ACTION_SCREEN_OFF).

Watch only this app's `OPSTR_SYSTEM_ALERT_WINDOW` with `AppOpsManager.startWatchingMode`. The API allows observing own-UID mode changes; unregister with `stopWatchingMode`. Marshal callbacks to the main thread and recheck `canDrawOverlays` before manipulating views. On revocation, remove the overlay, cancel animation/callbacks, mark floating mode inactive, remove the foreground notification and stop the service. Also check permission before every window add/update and catch window/security exceptions: a permission check is not an atomic lease. Do not repeatedly add a removed window on failure. [AppOps change observation](https://developer.android.com/reference/android/app/AppOpsManager#startWatchingMode(java.lang.String,%20java.lang.String,%20android.app.AppOpsManager.OnOpChangedListener)).

Stop should be idempotent across the app button, bubble, notification and destruction: invalidate the service generation, remove callbacks and the single attached view safely, unregister receivers/listeners, call `stopForeground(STOP_FOREGROUND_REMOVE)` and `stopSelf()`. For the minimal version, Hide has the same teardown and requires an explicit later Show/Enable. Return `START_NOT_STICKY`; keep active enablement session-scoped so a new process does not silently restart it. The existing `CompanionView` cancels animation on detach/visibility loss; the service must still drive visibility correctly and never render a listening state when there is no microphone session.

Android 13's Active apps Stop terminates the entire app and sends no callback. Do not depend on `onDestroy()` to update persisted state in that situation. A later manual app launch should report actual running state and offer an explicit start rather than interpreting a saved preference as permission to relaunch. [User-initiated FGS stopping](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping).

## Opening the assistant

Only an explicit tap on Mira/Open assistant may foreground the app. For the minimal bubble, use an explicit intent to our own activity from its click handler, with `FLAG_ACTIVITY_NEW_TASK` when using service context; recheck interactive/unlocked/attached state and catch a refused launch. Do not launch activities from nudges, timers, animation or lifecycle callbacks. The notification content should be an immutable `PendingIntent.getActivity` directly targeting that activity, not a service/broadcast trampoline. These are recommendations using Android's documented user-visible/overlay and system-notification launch paths. [Activity security and launch exceptions](https://developer.android.com/guide/components/activities/secure-bal).

If the implementation instead manually sends an activity PendingIntent from the overlay, apply the platform's sender opt-in rules: on API 36 prefer `MODE_BACKGROUND_ACTIVITY_START_ALLOW_IF_VISIBLE`; version-guard API 34/35's older sender mode. Target 35 creators no longer delegate their background launch privileges by default. Do not broadly enable creator privileges on tokens handed elsewhere merely to simplify UI. A failed tap should leave Stop usable and offer the notification/app launcher fallback. [PendingIntent opt-ins](https://developer.android.com/guide/components/activities/secure-bal#opt-in), [visibility-limited mode](https://developer.android.com/reference/android/app/ActivityOptions#MODE_BACKGROUND_ACTIVITY_START_ALLOW_IF_VISIBLE).

## Evidence required before claiming it works

After implementation and **user-granted** permissions, verify enable/deny/cancel, drag/tap separation, interaction outside the bubble, notification Stop, app Stop, repeated enable without duplicate windows, rotation/keyboard bounds, reduced motion, screen off, lock/unlock, permission revocation while running, overlay-suppressing screens and process/user stop. Verify stopping Mira leaves focus monitoring and timers unchanged. Record the actual APK hash/device/API and observed results; source compilation alone is insufficient.

Product wording should be “Mira can float while you use your unlocked phone, until you stop it or Android hides/stops it.” No absolute always-on or OEM-survival guarantee follows from a foreground service, overlay permission or successful Nothing-phone test. Test the eventual iQOO device separately; keep an in-app companion fallback. This report specifies a bounded local visual companion, not background voice recognition or general phone control.
