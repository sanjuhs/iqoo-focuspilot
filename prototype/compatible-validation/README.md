# Compatible unit validator development checker

This pure-Java research checker reuses the exact earlier unit-regression
1,582 prepared inputs/gold and all80 prior accepted proposal identities.
It also replays the24 already captured unit-native replies against unchanged
manual development gold. No model, phone, new corpus, training, dependency or
fresh qualification is involved. Original files remain immutable.

Preparation reads/pins only original evidence and checker sources. It does not
read or call the CompatibleUnitCommand candidate. Development tuples represent
the same canonical gold action/hour/minute/seconds/app; reasons and preview
wording are not preserved. Raw captured response text is used unchanged.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 prototype/compatible-validation/test_validation.py
python3 prototype/compatible-validation/validate.py prepare \
  --out prototype/compatible-validation/build/prepared
```

Preparation creates public aggregate `readiness.json`, exclusive private
development input/gold and fixed source hashes. Original known input/gold hashes
are literal pins. Original24 raw/process/detail records are pinned through the
actual unit independent-audit SHA. Candidate contents remain unread and calls
stay zero through this phase. Root must commit checker/protocol/readiness and
candidate/dependencies together before authorizing evaluation.

```sh
python3 prototype/compatible-validation/validate.py evaluate \
  --source-commit FULL_COMMON_FROZEN_HEAD \
  --out prototype/compatible-validation/build/evaluation
```

Evaluation requires exact current HEAD and byte equality with its committed
candidate, UnitCommand, StructuredCommand, CommandNumberWords, selected
ModelCommandGate and checker sources. It compiles isolated classes once, then
produces three distinct groups:

- **Known validator:** 1,582 unchanged fixed mock replies (158 supported oracle,
  476 unknown, 948 wrong supported-intent routes), with all80 prior proposals.
- **Development validator:** 24 existing model replies; 18 supported and6 unknown.
  Checks canonical full slots and all12 previously accepted correct proposals.
- **Development pipeline:** recognize(original), followed by validation of the
  same old model reply only when recognition refuses. Records origin as
  FAST_LOCAL_REQUEST, CHECKED_MODEL or UNKNOWN. This score is independent of
  raw model prediction accuracy and validator-only success.

The one evaluation claim prevents retries through another output-directory
alias. Outputs/classes are confined to ignored `build/` and directories/files
are exclusive. Each Java command has a30-second bound and executes no Android
tool. A partial or failed run remains preserved and cannot be scored as complete.
Hashes bind inputs, source, classes and actual decisions. Pre/postflight requires
unchanged source/input bytes and exact HEAD.

All80 prior accepted proposals must be preserved, all476 unknown and948 wrong
routes refused, and no supported oracle may be wrongly accepted. Both24-row
validator and pipeline must preserve all12 old correct accepted proposals,
refuse all6 unknowns and accept no wrong action/slots. Coverage out of158/18
is reported separately. Passing only permits a separate prospectively frozen
fresh qualification; it does not authorize integration or phone promotion.

These are known correlated synthetic development requests. Fixed mock replies
do not represent model predictions, and the earlier model capture is not new
inference. Finite passing routes establish no arbitrary-language safety, voice,
Android/NPU, Office Kit or user-outcome claim. A pipeline FAST_LOCAL_REQUEST
origin describes the local code path; replay timings cannot prove a product
speedup against the older capture.
