# Local task-draft feasibility lab

Pre-event host research, not eligible event-created code. This experiment tests
review-only planning text from the existing Qwen3.5-0.8B Q4_0 model and unchanged
host JNI library. It executes no phone or external action, reads no real account,
downloads nothing, and does not change the original command prompt or policy.

**This first candidate is rejected: zero useful drafts.** All 12 requests reached
actual EOS with `{"steps":[]}`, including all eight benign goals and the negated
benign goal. The grammar accepted every response, but there were no three-step
plans. The author review finds benign goal relevance/criterion coverage **0/8**;
three of four tricky-case criteria pass because their prewritten criteria allow or
require decline. Nine cases fail their requested guidance criteria. No access or
completion claim occurs because every response is empty; this is not evidence of
selective safety or a useful assistant. No app card or generation path should ship
from this candidate.

[Capture aggregates](results.json), [author review aggregates](qualitative-results.json),
[immutable freeze](freeze-manifest.json), [protocol](protocol.json),
[archived exact TaskDraft source](reference/TaskDraft.java).

The shared pure-Java `TaskDraft` contract owns the one agreed no-thinking prompt,
GBNF grammar, goal validation and strict three-step parser. An exact empty-array
response is an explicit decline, not a usable checklist. The research snapshots
that class, `TaskPlan` and `LocalModel` into ignored `build/source/`, compiles only
Java and uses the existing native library. No native compilation is performed.

Eight tiny public benign productivity fixtures and four tricky fixtures have
written goal-relevance/constraint criteria before any inference. The tricky cases
cover missing account access, negated scheduling, destructive requests and reserved
chat marker injection. This small informed, author-reviewed set is feasibility
evidence, not calibrated correctness, independent human validation or a safety
benchmark. JSON shape alone never establishes useful guidance.

## Reproduction

Run from the repository root with the already verified model/runtime present:

```sh
python3 prototype/task-draft-research/restore_reference.py
python3 prototype/task-draft-research/run_research.py verify
```

`restore_reference.py` reconstructs ignored source/input/prompt snapshots from the
public archive and fixture generator and verifies original hashes without loading
the model or generating tokens. It does not use mutable app constants or overwrite
different existing snapshots. The verification command additionally needs the
original local GGUF and host JNI at their manifest hashes. These large/compiled
prerequisites remain ignored; this source checkout does not bundle them.
The complete three-test run additionally needs an actual ignored capture and its
process record (from this workspace or a disposable reproduction):

```sh
python3 -m unittest discover -s prototype/task-draft-research -p 'test_*.py' -v
```

To reproduce this same first candidate, use a disposable checkout, restore this
original manifest/archive, run the recovery helper, then run `capture` and
`summarize` there once. Original raw capture files are absent on a public checkout,
so a new capture has its own timings/output evidence; never overwrite this
repository's original records. The results summary's initial `qualitative` field
retains its pending-at-capture wording; completed subjective review is a separate
hash-bound `qualitative-results.json` generated by the review command below.

To test a second candidate, create a **new sibling experiment directory** under
`prototype/`, copy only `generate_data.py`, `run_research.py`, `TaskDraftEval.java`
and `test_research.py` there, and author a fresh fixture set with prewritten
criteria. Do not copy or overwrite first-candidate reporting files/build/archive.
Agree and freeze the new shared TaskDraft source before any model run. Then use
that directory's runner with the new source digest:

```sh
python3 prototype/NEW_EXPERIMENT/run_research.py freeze --contract-sha NEW_AGREED_TASKDRAFT_SOURCE_SHA
python3 prototype/NEW_EXPERIMENT/run_research.py capture
python3 prototype/NEW_EXPERIMENT/run_research.py summarize
```

The freeze verifies the existing 563,036,064-byte GGUF and host JNI digests, compiles
the exact shared classes, inventories actual rendered prompts/grammar without
model generation, and binds source/data/prompt/grammar/model/native hashes.
`capture` refuses to rerun an attempted capture. Each request gets fresh KV and
recurrent state, CPU context1024/four threads, greedy sampling, max128 tokens,
capturefalse and a 20-second native cancellation deadline. The whole process has
a 300-second deadline. Raw goals, prompts, outputs, parser traces and qualitative
notes remain in ignored `build/`; aggregate results are public.

Actual EOS and the strict shared parser determine completion/schema counts;
declines are counted separately. After reviewing every raw output against its
prewritten criterion, write `build/qualitative-review.json` with one record per ID:
`id`, `criterion_met`, `goal_relevant`, `respects_constraints`,
`invented_access_or_completion` (all four judgments explicit booleans), and a
written `reason`. Run:

```sh
python3 prototype/task-draft-research/run_research.py review
```

That command binds the author judgments to the unchanged capture and generates
aggregate `qualitative-results.json`, without new inference or prompt selection.
It rejects missing cases, duplicate IDs, incomplete-generation passes and a
claimed explicit-decline pass on a nonempty response. Timings are host-only and
exclude a phone UI, voice, scheduling and Android lifecycle. No learned weights
or training checkpoints are produced.

Measured first capture: load **453.89 ms**, warm native median **303.44 ms**,
first native request **300.67 ms**, total process **4.253 s**, prompt length
118–132 tokens and exactly four generated tokens for every decline. All calls
report CPU-only/capturefalse and empty activation arrays. These fast refusals do
not predict the latency of a real three-step draft. Three focused research tests
pass after capture; architecture separately reports eleven shared-contract JVM
tests. No phone performance evidence was collected.

`native-dependencies.json` is a read-only installed-library inventory collected
**after** capture, not a pre-capture dependency freeze. The JNI binary is linked
against installed Homebrew llama build9620 and ggml0.16 dynamic libraries. The
freeze's `native_llama_commit` records the existing pinned wrapper/header source
lineage; it does not independently certify installed dependency source commits.
Their actual paths, sizes and SHA-256 hashes are supplied separately for honest
reproduction. There was no native rebuild or dependency installation in this lab.

## Integration boundary

Only completed, strictly parsed, goal-associated output may enter a review screen.
The three strings remain inert and unsaved until a user accepts an editable draft
and separately saves it. Changing the saved goal, cancellation, backgrounding or
destruction must invalidate late results. A decline or incomplete/invalid output
offers manual checklist editing. Model wording can still be irrelevant, false or
unsafe despite valid JSON; it must never become command authorization, a claim of
account access/completion, or automatic execution. Useful host evidence alone
does not prove phone performance or justify broad autonomy.
